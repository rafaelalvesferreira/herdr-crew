# v0.4 design: the `lead` role and guaranteed models

Status: implemented in v0.4.0.

## Intent

Let one helper split a larger task among cheaper subagents and hand back one integrated result, with the coordinator (the expensive model) doing only the planning and the review. And make the model each agent runs on something the user sets once and can see, not something that falls out of defaults.

## Goals

- A coordinator can delegate a task that has several independent parts to a single helper pane.
- The user controls which model the coordinator, each helper role and the subagents use, from one file.
- The model an agent actually started with is visible.

## Non-goals

- Several helper panes in several worktrees for one task (heavy setup, merge at the end).
- A headless batch runner over the API.
- Codex as a `lead`.

## Anti-goals

- Splitting work that does not split: parts written in isolation that do not fit, with the review costing more than the split saved.
- A subagent silently running on a weaker or a more expensive model than the user chose.

## Approaches considered

| Approach | Trade-off |
|---|---|
| **A helper fans out internally with subagents** (chosen) | Small change: one role, one contract block, two routing keys. One process edits the tree, so "one editor per working tree" still holds. Subagents do not show in the Herdr sidebar. |
| The coordinator opens N helpers in N worktrees | Each one visible and isolated, but per-worktree setup, a trust dialog per folder and a merge at the end. |
| A batch command running `claude -p` per task file | No panes and closest to a plain API loop, but nothing to watch or steer, and a second execution path to maintain. |

## Design

### When a task gets a `lead`

The coordinator decides, with an observable test. All three must hold:

1. The task has three or more parts that touch different files.
2. The interface between the parts can be written down before any part starts (signatures, types, data shapes).
3. Something can be run at the end that shows the parts fit (tests, build).

One missing: a regular `builder`.

### Who plans

The coordinator writes the plan. It has the user's request, the decisions already made and the architecture. The plan is in the contract file, so the user can read it before anything is spent.

### Contract

`helper-start --role lead` produces the builder contract plus one block, between TASK and COMPARISON_BASE:

```
PLAN: <FILL: one entry per part>
  part <n>: <what> | files: <paths this part owns> | interface: <what it exposes or consumes> | done when: <check>
CHECK: <FILL: the command that shows the parts fit>
```

Fixed text written by the script, which `send` refuses to see altered:

- one subagent per part, each editing only that part's files;
- the lead integrates, runs CHECK, and fixes what CHECK shows;
- no part is skipped or merged into another without saying so in the report;
- the report lists each part with its outcome, then the CHECK result.

`send` requires at least three parts and a non-empty CHECK for a `lead`.

### Models

Routing file, same lookup order as today, two new keys:

```json
{ "coordinator": "opus", "default": "sonnet", "reviewer": "opus", "subagent": "sonnet" }
```

- `default`: used for any role without its own key.
- `subagent`: the model for a lead's subagents. The script sets `CLAUDE_CODE_SUBAGENT_MODEL` in the lead's pane before starting it. No `subagent` key: the variable is not set and subagents follow the lead's model.
- No routing file at all: agents start on the user's Claude Code default, as today. The script does not refuse.

The example file changes its cheapest entry from `haiku` to `sonnet`.

### Visibility

- `helper-start` and `worktree-create` report the model they passed and which file it came from; the coordinator says it in the line where it tells the user the helper started ("`lead-1` on sonnet, subagents on sonnet").
- `map` gains a `model` column: the model the agent last answered with, read from its session transcript (the process command line does not expose `--model`). Before the first answer it shows what the script passed, marked `(requested)`.

## Left to the builder

- Exact wording of the fixed lead instructions.
- How `map` extracts `--model` from the process arguments.

## To verify in a real run before release

- A lead started with `CLAUDE_CODE_SUBAGENT_MODEL` set really runs its subagents on that model (the installed Claude Code knows the variable; its effect is untested here).
- A lead with three parts in the smoke test: parts land in their own files and CHECK passes.
